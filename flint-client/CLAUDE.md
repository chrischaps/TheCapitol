# CLAUDE.md: The Capitol, Flint client

The Capitol's 3D client, built on the Flint engine (Rust/wgpu). It's a window onto the Capitol server: Rust handles the wire and the world, and Rhai scripts handle the feel. The plan is `../the-capitol-flint-client.md`, and the work queue is the GitHub issues labelled `flint-client` (use the `next-issue` skill).

## Layout

```
flint-client/
  Cargo.toml          # its own workspace: members crates/*, excludes engine/
  Cargo.lock          # committed; seeded from engine/Cargo.lock
  .cargo/config.toml  # 8 MB main-thread stack on Windows (copied from the engine)
  engine/             # Flint, git subtree (squash). Don't edit casually; see below.
  crates/
    capitol-core/     # net + state, no engine dependency, fast tests
    capitol-client/   # the game binary (`capitol`)
  scenes/ schemas/ scripts/ fonts/ audio/ models/ fixtures/
  particles/          # *.particles.toml effects, loaded by name (the forge's fire, P6.1)
  assets/icons/       # item icons: <item_type>.svg, fallback.svg; style in its README (P5.2)
  play.bat            # build release and run
  renders/            # screenshots and captures (gitignored)
  target/             # this workspace's build output (gitignored)
```

The root `Cargo.toml` (the backend workspace) has `exclude = ["flint-client"]`. Run cargo from `flint-client/`, not the repo root.

**Engine crates are path dependencies.** They're declared once in `[workspace.dependencies]` in `Cargo.toml` (`flint-player = { path = "engine/crates/flint-player" }`). Member crates use `{ workspace = true }`. The engine's own workspace is excluded rather than nested. Its crates still pick up `version.workspace = true` and similar settings from `engine/Cargo.toml`.

**The wire types come from `../protocol`** (crate `capitol-protocol`, a member of the root workspace). It holds the WebSocket enums, REST DTOs, `/terrain` types and shared rules (ranges, zones, quality grades, the water-crossing test). The backend compiles against the same crate, so use its types rather than redefining shapes here. The client leaves its `backend` feature off. Change the protocol from the repo root, and run `cargo test -p capitol-protocol` there.

**Match the engine's versions.** A third-party crate that crosses the engine boundary (egui, winit, wgpu, rhai, glam) must use the same version as `engine/Cargo.toml`. Otherwise two copies get linked and the types don't line up.

## Build and run

```bash
cd flint-client
cargo build                         # debug, about 45 s from cold
cargo test -p capitol-core          # fast; no engine
play.bat [args]                     # release build, then target\release\capitol.exe [args]
```

From bash, run `play.bat` through PowerShell with an absolute path:
`powershell.exe -NoProfile -Command "cmd /c 'C:\Users\chris\dev\TheCapitol\flint-client\play.bat'"`.

If another build or a running client could lock the exe, use your own `CARGO_TARGET_DIR`.

**Packaging (P8.7).** `powershell -NoProfile -File package.ps1` builds into `target\package` with a static C runtime (`+crt-static`, so no VC++ redistributable; its `RUSTFLAGS` repeat the 8 MB stack, because they replace `.cargo/config.toml`'s). It stages `dist\TheCapitol\` and zips it as `dist\TheCapitol-<git describe>.zip` (`dist/` is gitignored at the root). The zip holds the exe, the game's data dirs, `engine\schemas` (the only engine files read at run time; the shaders are compiled in), `fixtures\terrain.json`, an `Explore offline.bat` and a player's `README.txt`. **A new data dir the game reads must be added to the script's list.** The game finds its data beside the exe when the working directory lacks the scene (`enter_game_dir` in `main.rs`), so the zip runs from a shortcut or any terminal; paths given on the command line are made absolute first. To check a package, unzip it outside the repo and run it from another folder: offline, then with `--server`, then signed in (a `save\session.toml` with `server`, `email`, `refresh_token` and `token_server` keys skips the form).

**Showcase.** `powershell -NoProfile -File tools\showcase.ps1` writes offline stills of every fixed `--view` and a crane shot (`capitol.mp4`, ffmpeg) into `renders\showcase\`. It runs with `--clean` (offline only: no inscription panel and no free-point mark) and its own settings file (High shadows). The clip is `--camera-path tools\showcase-path.txt` ([#92](https://github.com/chrischaps/TheCapitol/issues/92)): the tower on the wilderness horizon, then round and in over the rings and up to the map.

## Terrain, offline mode and captures

`capitol` fetches `/terrain` from the server and caches it in `cache/terrain-<host_port>.json` (gitignored). A cached terrain is drawn at once and revalidated by version: the server answers 304 while it's current. The server is `--server` (or `CAPITOL_SERVER`) for one run, otherwise the one last chosen on the login form, otherwise `http://localhost:3000`.

**Login (P4.1).** Online, the client opens on the login form (`ui/login.rs`), with the camera circling the tower behind it (`camera.rhai`, `cap_at_login`). A stored token goes straight in. The way in is `capitol_core::auth::Auth`, which is pure and unit-tested; `session.rs` owns the `Net`, the store and the poller, and runs it. The server, the last email and the token live in `save/session.toml` (gitignored; never commit it), not in the scripts' `save/persist.toml`. Delete the file, or Sign out (top right), to see the form again. **Players (P4.2)** are `entities.rs`: an avatar entity per `Motion` pose, with fades on join and leave. Their names are `scripts/hud.rhai`, and so is the zone banner (P4.5). The header strip and the reconnecting overlay are `ui/hud.rs`. **Clicks (P4.3)** are `scripts/input.rhai`: a left click on the ground goes through the click priorities (React's order, 1–5 still empty) to `cap_move`. A canal stops the walk with `movement_blocked`, which the extension fires at the scripts. **Resource nodes (P4.4)** are `nodes/` (every kind since E2.5, below) and priority 5 in `input.rhai` (`cap_node_at`, `cap_extract`, the rings and toasts). The click rule, extract or walk then extract, is `capitol_core::harvest`. To extract without clicking, `POST /world/extract` with the account's token while the client is connected. The client sees it like its own. **Input scripts click (H16, Flint ADR 0082):** `3.0 click 640 360` moves the pointer, presses and releases on three frames, `mouse x y [secs]` moves or glides it (a drag, with `down`/`up MouseLeft`), and `MouseRight` etc. work with `down`, `up` and `tap`. Positions are the screenshot's pixels. The pointer goes through egui first, as a real one does, so a click on a panel presses its button and never reaches the world. Keep the real cursor off the window during a capture. To reach a canal fast, walk there first with `POST /player/move` while the client is connected. To see a crowd, run `capitol-bot --accounts 10 --wander --near <your name>`. A stored token in `save/session.toml` is the easy way to put a capture in the world without typing into the form. Once signed in, the session hears `terrain_updated` (an admin regenerating the world from the React client's F2 tweaker) and rebuilds the world. Only the layers whose inputs changed are rebuilt (`world::Rebuild`). The form can't be typed into from `--input-script` (it writes actions, not egui text); P4.1 drove it with keys posted to the client's window by PID, see its closing comment on #31. `--offline <file>` builds the world from a `/terrain` JSON with no server at all, so there's no login either: the rig, as before. `fixtures/terrain.json` is a captured one; refresh it with `curl -s -o fixtures/terrain.json http://localhost:3000/terrain`.

Every visual change is checked with a capture, run from `flint-client/`:

```bash
target/release/capitol.exe --offline fixtures/terrain.json --screenshot-at 3 --exit-after 4
```

That writes `renders/capitol.png`. The camera is the rig in `scripts/camera.rhai` (P3.9): signed in, it follows your avatar and WASD or the arrows pan from it (P4.2). Offline, WASD moves a free point, the wheel or R/F zoom from 15° over the street to the map, Q/E or a right-drag orbit, H comes home. Keys are in `config/input.toml`. `--view` picks where it starts: `street`, `district` and `map` are rig zooms. `bridge|suburb|urban|capitol|crown|from-urban|from-suburban|from-rural|from-wilderness` are fixed shots (bridge stands on a canal quay; suburb is low over curving streets; urban is close over the urban lots; capitol looks up at the tower from beyond the moat; crown is level with its lantern; each from-* puts the tower on the horizon from that zone). A shot holds until the first camera input, then eases into the rig. The rig takes up what the shot was looking at, zoomed out just enough to keep a raised subject like the crown mid-frame and no wider than `district`, so Q/E orbit round it. **To film a deliberate move,** pass `--camera-path <file>` (offline only). The file has one key a line, `t px py pz tx ty tz`: game seconds, then where the camera stands and what it looks at, in world metres. It plays as a moving shot on a monotone cubic, starting and ending at rest; a repeated key is a hold. It stays at its last key until camera input lets go into the rig. The format is in `camera_path.rs`, and `tools/showcase-path.txt` is an example. For motion from held keys instead, add `--frame-step 0.016666667 --screenshot-every 0.25` with an `--input-script` (`2.0 wheel 3` scrolls three notches in; R/F zoom at a steady rate) for numbered, deterministic frames. `cargo test -p capitol-client camera_rig` checks the rig's geometry: no clipping, the tilt curve, the horizon, the map. `--screenshot <path>` names the file, `--input-script <file>` plays timed keys and the wheel (flint-player's format: `1.0 tap KeyE`, `1.0 wheel -2`), and `--exit-after` prints the average ms/frame and, on a second `[perf]` line, the average draw calls, entity draws, culled draws and triangles. `--stats` opens F2's rendering stats overlay from the first frame, and an input script can tap F2 (or F3/F4) like a real key (H9). The old `RUST_LOG=capitol=debug` stats log is gone: use those instead. Look at the PNG before calling a visual change done. The scene is `scenes/capitol.scene.toml` (dusk: sky, sun, fog and post). The dusk is the evening of the day (`daylight.rs`, P8.6a): online the light follows the server's clock, and offline it's evening unless `--time-of-day <0..1>` says otherwise (0 is midnight, 0.25 dawn, 0.5 noon, 0.8 evening). The `sun` and `fill` lights and the sky are rewritten as the hour moves, so tune the dusk in the scene file and the other hours in `daylight.rs`. Its fog thins as the camera climbs and is gone by 250 m (density zero; fog stays on, and since Flint ADR 0078 it reaches everything drawn, water included, so `far` is just past the 5 km ground skirt), and from 280 m to 600 m the light flattens into the map's palette (`atmosphere.rs`), so a high view shows neither.

## The UI theme

All egui panels take their look from `crates/capitol-client/src/ui/theme.rs` (P5.1, plan §4.3). It holds the colour tokens, egui's `Style` and `Visuals`, the fonts, and the parts panels are made of (`panel`, `well`, `tray`, `header`, `pill`, `primary_button`, `accent_button`, `grade_badge`, `quality_badge`, ...). **Panels use no colours or sizes of their own.** If a panel needs one that's missing, add it to `theme.rs`. `theme::install` runs at the top of `CapitolExtension::ui` and sets the style once.

The fonts are in `fonts/`: Source Sans 3 (text) and Cinzel (titles), both OFL, with licences beside them. Flint installs them for the script HUD and egui alike. `fonts.toml` names them `body`, `strong` and `display` (`draw_text_opts(..., #{ font: "display" })`, `FontFamily::Name("strong")`), and its `[egui]` table makes `body` egui's default face (Flint ADR 0081, #72). Don't call `set_fonts` from the game: Flint's next font install would drop it. A font that can't live in `fonts/` goes through `PlayerExtension::fonts`. Tests that draw the theme take their context from `theme::test_context()`, which loads the fonts Flint would.

Review a theme change side by side with the React client, from `flint-client/` (the steps are in the file's header comment too):

```bash
target/release/capitol.exe --offline fixtures/terrain.json --ui-sample --width 1920 --height 1080 --screenshot renders/p5.1-sample-flint.png --screenshot-at 3 --exit-after 4
target/release/capitol.exe --offline fixtures/terrain.json --width 1920 --height 1080 --screenshot renders/p5.1-world.png --screenshot-at 3 --exit-after 4
"/c/Program Files/Google/Chrome/Application/chrome.exe" --headless --allow-file-access-from-files --window-size=1280,720 --force-device-scale-factor=1.5 --screenshot="$(cygpath -w $PWD/renders/p5.1-sample-react.png)" "file:///$(cygpath -m $PWD/tools/theme-sample.html)"
```

`tools/theme-sample.html` is the sample's two panels in the React markup and CSS, with the panel-less world capture as the backdrop.

**Slots (P5.3).** Every container is drawn with `ui::slots::SlotGrid::new(&container).show(ui, &mut icons)`, which returns `Option<Move>`. Send the move with `session.move_item(m)`, and show `session.move_refused(now)` when it's `Some`. Don't draw slots by hand. A drag between any two grids on screen just works (egui DnD payload). **The inventory panel (P5.4)** is `ui/inventory.rs`, bottom right, toggled with `I` (the `inventory` action, so `--input-script` can press it) or the header's Inventory chip. `--containers` shows, bottom left, any container no panel has taken. Today every type has its panel, so it's empty. `--ui-sample`'s grids move, merge and swap locally, so the widget can be tried offline. `cargo test -p capitol-client slots` drives drags headless. With the stack up, `capitol-bot --prefix slots` once, then `cargo test -p capitol-client a_move_reaches -- --ignored`, checks the server round trip. Captures drag with the input script's pointer (`1.0 mouse 950 345`, `1.2 down MouseLeft`, `1.3 mouse 1105 425 0.5`, `2.0 up MouseLeft`), and a hover of half a second shows the tooltip. `--ui-sample` is the offline bench for it.

**Crafting (P5.5).** The panel is `ui/crafting.rs` and its rules are `capitol_core::craft`. `Session::craft(now, recipe_id)` checks and sends; `Session::crafting()` is where the craft stands. The ring and the finish are in `scripts/input.rhai` (`cap_players()`' `craft`, and the `crafting_completed` event). C (the `crafting` action) or the header's Crafting chip toggles the panel, and Enter (`craft`) crafts, so an `--input-script` can craft: `7.0 tap Enter`. With the stack up, `cargo test -p capitol-client rope_then -- --ignored` runs Fill, rope, a blocked kit, a cancel and the kit through `Session`. It gathers its own fiber on `craft1@bots.capitol.local`. To stock any account for a capture, use `capitol-bot --prefix <p> --gather <n>`. Arrange the boxes with input-script drags, or beforehand with `POST /inventory/move` using the token in `save/session.toml`.

**Stations (P6.1)** are `stations.rs` (the models, from the store) and `draw_station_ring` in `input.rhai` (from `cap_stations()`). The reach rule is `capitol_core::station`, the place for P6.2's placement checks too. The forge's fire is `particles/forge.particles.toml`: Flint loads every effect in `particles/` at start, and `stations.rs` names it in a `particle_effect` component. The kiln's smoke is `particles/kiln.particles.toml`. Since E2.6 every catalog station has a model (a new type without one is a plank crate; `every_catalog_station_has_its_own_model_and_unknown_ones_a_crate` fails until it gets one), and fired ones glow brighter at night (`Stations::fires`). To see them all offline, `--station-sample` stands one of each in a row where the camera looks, 0.5 s in. Frame it with a `--camera-path` that holds still past 0.5 s, e.g. one key `0 -46.9 2.3 336.2  -50.4 0.7 330.1` in the rural ring, and add `--time-of-day 0.02` for night. **The station panel (P6.3)** is `ui/station.rs`, bottom right beside the inventory. Click a station (`input.rhai` priority 3, `cap_station_at`), or press O for the nearest one. Out of reach, you walk to it first (`capitol_core::station::Visit`). Enter crafts at the open station. So an `--input-script` can open one and craft: `3.5 tap KeyO`, then `8.0 tap Enter`. Every station recipe is content (`backend/content/recipes.toml`, D5 since E2.4): the workbench's simplest is `tool_handle` (2 sticks and a rope), and the forge kit takes bricks, stone and rope under a hammer. Its output lands in the player's crafting output slot, not the station's box.

Placing a station needs a kit and an owned plot (P6.2, below), so for a quick test insert rows straight into the local DB beside an account. Give each its `station_inventory` container, or `open_station` answers "Station has no container":

```bash
docker exec capitol-postgres psql -U capitol -d capitol -c "with s as (insert into stations (id, station_type, owner_id, position_x, position_y) select gen_random_uuid(), t, p.id, x, y from players p, (values ('workbench',3960::real,7330::real),('forge',4050,7330),('storage_chest',3955,7400)) v(t,x,y) where p.name='Stations1' returning id) insert into containers (id, container_type, owner_id, station_id) select gen_random_uuid(), 'station_inventory', null, id from s"
```

The live station test crafts a tool handle, and fallen branches have no nodes until E2.3 (#162), so give `Stations1` its two sticks the same way:

```bash
docker exec capitol-postgres psql -U capitol -d capitol -c "insert into items (id, item_type, quality, quantity, owner_id, container_id, slot_index) select gen_random_uuid(), 'sticks', 50, 2, p.id, c.id, (select coalesce(max(slot_index), -1) + 1 from items where container_id = c.id) from players p join containers c on c.owner_id = p.id and c.container_type = 'player_inventory' where p.name = 'Stations1'"
```

**Restart the backend afterwards** if you'll craft at them: the tick loads stations only at startup or from `place_station`, and `craft_at_station` checks its own list ('Cannot access station'). Opening one and moving items work without a restart. `capitol-bot --prefix stations --gather 0` makes `Stations1` at the spawn, and its password is `stations-1-capitol-bot`, so `POST /auth/login` with `"refresh": true` gives the `refresh_token` for `save/session.toml` (without it there's no refresh token, and the form shows). Rows inserted this way fire no `station_placed`, so they rise rather than drop. Delete them when you're done, because new players spawn right there. P6.3 tested on its own database instead: `create database capitol_45` in the same container, with `DATABASE_URL` and `PORT` in the worktree's `backend/.env`. That keeps a new migration off the shared DB until it lands; a backend whose folder lacks an applied migration refuses to start. With a workbench and a chest for `Station1`, `cargo test -p capitol-client a_station_opens -- --ignored` runs it all through `Session`: walk and open, Fill, craft a tool handle, the chest in and out, walk away, remove. It removes the chest.

**Tools and wear (E1.7).** A tool's slot shows a wear bar in place of the quantity, and its tooltip the numbers the server uses (`slots::tool_lines`; the catalog reaches the slots through `slots::know_catalog`, once a frame). The craft check counts the tool term: `craft::tool_for` (or `tool_in` from a `GameState`) picks the tool as the server does, and the preview's bar, key, tool line and lifts are `crafting::preview`, shared with the station panel. The station's tool slot is `station::tool_slot`; a drop on it is `install_tool`, and a drag of the installed tool onto any slot becomes `remove_tool` in `Session::move_item`. A broken tool shatters where its slot was last drawn (`slots::shatter`, from `tool_broke`). Offline, `--ui-sample` shows sickles at three wear levels, breaks one at 6 s (`--frame-step 0.016666667 --screenshot-every 0.05` to film it), and its preview is the real one; hover a sickle with `1.5 mouse 1667 861` at 1920×1080 for its tooltip. Since E2.4 the anvil's four heads and the four station kits take a hammer, so a tool term shows live at an anvil, or at a workbench on `craft_kiln`.

**Plots (P6.4).** The panel is `ui/plot.rs` and its rules are `capitol_core::plot::Offer`. Alt-click is `select_plot` in `input.rhai` (`cap_pick_plot`), and the store's `picked_plot` is what it shows. `GameState::plots()` holds only your plots (the poller asks `/plots?owner=<you>`), and `world::plots::owned` draws them in gold as the `plots_owned` mesh. With the stack up, `capitol-bot --prefix plots --gather 0` makes `Plots1` (password `plots-1-capitol-bot`). Set it on an unclaimed plot with Strands enough for the deed: `update players set position_x=3841, position_y=7059, strand_balance=600 where name='Plots1'` is a rural estate by the spawn, deed 250. Then `cargo test -p capitol-client a_plot_is_picked_and_claimed -- --ignored` picks and claims it through `Session`. The test signs out, which ends the stored token, so log in again before a capture. To release the plot afterwards: `update plots set owner_id=null, claimed_at=null, assessed_value=0 where terrain_id='rural_plot_trail_3_L_2'`. Alt-click in a capture: hold Alt from `--input-script` (`6.0 down AltLeft`) and `click` the lot, then `click` the Claim button.

**Nodes (E2.5)** are `nodes/`: `models.rs` builds a model per resource type (grass, trees in four species, branches, outcrops, iron veins, clay banks, a cairn for unknown ids), each with a full, a lit and a spent look, and `mod.rs` places them. A node at rest is baked into its sector's mesh (`nodes_r3w05`). Only one that's changing (aimed at, worked, taken, regrowing, new) has an entity, `node_<id>`, with a `gather_*` particle effect while worked. The store holds every node (`/world/nodes` with the snapshot), so the woods stand on the horizon. Offline, `--node-sample` lays out a row of each kind and a wood round where the camera looks half a second in, and loops them through being worked (4–7 s), taken (7 s), spent and back (13 s). Put it in the rural ring with a two-key `--camera-path`, so the layout happens at the first key: `0 -58.6 25.6 350.7  -55 0.6 330`, `0.7` the same, then where you want to look. `cargo test -p capitol-client nodes` checks the sizes, the spent looks, the windings, the baking and the fall. Placement goes through `nodes::ground_at`, for W9.

**Houses (P8.6b)** are `world/houses.rs`: one on every claimed lot, everyone's, from the store's `claimed_lots()` (`/plots/claimed` with the snapshot, then WS). A claim seen within 8 s of being made grows over 4 s; older ones are simply there. Each sector's houses are one mesh (`houses_r1w07`), the windows are one mesh per quarter ring, dark glass (`houses_windows_r1q2`) and lit (`houses_lamps_r1q2`). The lit ones glow with the hour through their entities' `material.emissive_scale` (`houses::lamp_light`; H23, Flint ADR 0090), so the hour never rebuilds a mesh. Houses going up are `houses_growing` and `houses_growing_lamps`. Every choice is seeded from the plot id, so change a style and every client's city changes alike. Offline, `--claim-sample 0.6` claims that share of the lots and `--grow-at 2` claims the 8 lots nearest the camera at 2 s, so they grow: `--claim-sample 0.3 --grow-at 2 --view suburb --frame-step 0.016666667 --screenshot-every 0.8`. `cargo test -p capitol-client houses` checks that every house stays on its lot and faces its street, the growth order, and the windows by day and night. Online, claim a lot as another account (`POST /plots/{id}/claim`) while the client watches. A release needs an admin terrain commit with force today; there's no foreclosure yet (#131).

**Grass (P8.6c)** is `world/grass.rs`: a CPU-painted mask over the whole world, handed to Flint's compute grass (`set_grass_ground`, H21). Repainted whole when the ground, roads or plots rebuild. A node's clearing is written in place as the node comes or goes, about 17 texels square (`update_grass_mask`, Flint ADR 0093, #135). The tuning is `grass::config` and the `GRASS_*` tokens in `palette`. The fixed `--view`s don't reach the fields, so capture it with a `--camera-path` in the rural ring (radius 300–380 m), e.g. one key `0 -59 1.8 335  0 2.0 0` for eye height with the tower on the horizon, or `0 -58.6 25.6 350.7  -55 0.6 330` for street zoom. `cargo test -p capitol-client grass` checks the rings, the roads, the lots, the water and the clearings. F3's Grass Debug panel tunes it live.

**Placing (P6.2).** The rules are `capitol_core::station` (`check`, `Placing`); `Session::begin_placing`, `place` and `cancel_placing` run them. The ghost is `Stations::ghost`, and the marks round it are `draw_placement` in `input.rhai`, from `cap_placing()`. A right click on a kit in the inventory starts it. Esc or a right click on the world stops it (`on_window_event`). A capture can right-click the kit (`click x y MouseRight`), or use `--place workbench_kit`, which starts placing once the inventory holds that kit. Put the pointer at the window's centre (`mouse`) before anything else, or the ghost starts at the corner. To set up an account: `capitol-bot --prefix place --gather 0`, then in the DB give it kits (`insert into items ... 'workbench_kit' ...` into its `player_inventory` container) and a plot (`update plots set owner_id=... where terrain_id='rural_plot_trail_3_L_3'`, the lot nearest the spawn), then walk it there with `POST /player/move` while the client is connected. Offline players don't walk, and the server keeps a player's position in memory, so a DB update to `players.position_*` doesn't move them.

**The exchange (P7.2).** The panel is `ui/exchange.rs` and its rules are `capitol_core::exchange`. Its numbers are `protocol::rules::deposit_quote`/`withdraw_quote`, the functions the server charges with, so don't recompute the fee anywhere else. X or the header's Exchange chip toggles it. `--exchange deposit` opens it with every fiber stack ticked, and `--exchange withdraw:200` with 200 typed: captures can click egui now (H16), but still can't type into it. With the stack up, `capitol-bot --prefix exchange --gather 12`, then `cargo test -p capitol-client an_exchange_charges -- --ignored` deposits every stack, withdraws 5 back and has a withdrawal refused, checking each answer against the preview to the Strand. A stack of 200 or more fiber is what makes the deposit fee non-zero: `update items set quantity=450 where item_type='fiber' and owner_id=(select id from players where name='Exchange1')`.

**The market (E3.5).** The panel is `ui/market.rs` and its rules are `capitol_core::market` (`Draft`, `quote`): the fee is `rules::market::listing_fee`, the server's, so don't work it out anywhere else. M (the `market` action) or the header's Market chip toggles it; `Session::set_market_open` and `watch_market` keep the summary, your orders, the box and the shown item's book coming. Fills are toasts (`market_note`). Offline, `--market-sample` opens it on a sample book; `--market plank:buy:12@42:C` presets the item and the form on either, as captures can't type into egui. Check the layout at 1280×720 (150% scaling makes that 853×480 points), the tightest case. Live: run the backend from your worktree on its own database and port (`create database capitol_<n>`, `DATABASE_URL` and `PORT` in `backend/.env`), then `CAPITOL_SERVER=http://127.0.0.1:<port> cargo test -p capitol-client a_market_order -- --ignored`. New accounts start with 100 Strands. To fill a book for a capture, give an account Strands and stacks in the DB (`items` plus `item_units`, whose trigger sums them) and `POST /market/orders` with its token.

**The Exchange hall (E3.7)** is `world/hall.rs` (the building, from `/terrain`'s `landmarks`), `capitol_core::hall` (the click: open in range, or walk to the door and open on arrival; and `goods_waiting`), the hall's marks in `input.rhai` (`draw_hall`: the outline, the prompt, the motes; from `cap_hall()`), and the header's "Goods at the hall" chip (`hud::hall_chip`, its arrow from `hud::bearing`). Offline, `--hall-sample` stands you where the camera looks with goods in the box, so the motes show, and the prompt when the camera looks at the hall; the header (and its chip) is online only. In the fixture it's at world (4.5–12.5, 24.75–34.75), east of the avenue between the moat and the inner canal: from the inner canal's south bridge, a one-key `--camera-path` of `0  -9 15 60  7 2 31` is street zoom on it. Add `--time-of-day 0.9` for the lit glass. `cargo test -p capitol-client hall` checks that it stays on its footprint, faces its normals, keeps the door clear and its clock right.

**Sound (P8.1)** is `crates/capitol-client/src/sound/`. `library.rs` synthesizes every sound in memory, on a thread started by the first frame, and the `Soundscape` (`mod.rs`) hands them to Flint with `ctx.audio.load_samples` (H18, Flint ADR 0084). Nothing is written to disk, and the scene doesn't preload `audio/` (`preload_audio = false`). `mod.rs` also holds `mix` (zone, water and height to bed levels) and the one-shot scheduling, all unit-tested (`cargo test -p capitol-client sound`). One-shots play straight from `pre_update` with `ctx.audio.play`. A bird or a rustle plays where it is, and Flint fades it with distance from the camera (32 m to 1250 m, `rolloff` 0.6; H20, #94), and the beds are `audio_source` entities on the music bus, spawned once the library is in. `--mute` silences it, and so does `--exit-after`, so captures make no noise. `RUST_LOG=capitol=debug` logs each one-shot and when the library is in. To check a recipe change without ears, `capitol --write-sounds <dir>` writes every sound as a WAV; draw their spectrograms (P8.1 used numpy and matplotlib): look for vertical lines (clicks, a sound cut off while ringing) and long horizontal smears (reverb ringing at a pitch).

**Juice (P8.2).** Every toast goes through `scripts/notices.rhai`'s stack: fire an event with a `title` and `body` (as the `*_note` events do) and add its name there. Don't draw toasts anywhere else. Pickups fly to `cap_ui_anchor("inventory")`, which Rust fills from wherever the panel or header button was drawn, and `cap_ui_pulse` lights it. Another landmark would be one more entry in `Shared::anchors`. The script HUD draws under egui, except what's drawn between `push_over_ui()` and `pop_over_ui()` (Flint ADR 0085, #96). The pickups use it so they land on the panel or button. Keep toasts and anything long-lived under it. To see it all without a server or an A-grade node:

```bash
target/release/capitol.exe --offline fixtures/terrain.json --juice-sample --frame-step 0.016666667 --screenshot-every 0.2 --screenshot renders/juice.png --exit-after 9
```

**Trading (P7.3).** The rules are `capitol_core::trading` (`Approach` for the shift-click, `Draft` for your side, which sends itself once it settles); `Session::trade_with`, `answer_trade`, `accept_trade`, `cancel_trade` and `draft_mut` run them. The panel is `ui/trade.rs`: the request card under the header, the window bottom centre. Shift-click is priority 2 in `input.rhai` (`cap_player_at`, `cap_trade_with`), and the strand between you is `draw_strand`, from `cap_trade()`. T (the `trade` action) accepts a request, or asks the nearest player, so an `--input-script` can answer one: `12.0 tap KeyT`. Captures can drag and press Accept with the input script's pointer (H16); `--trade-offer rope:5` drafts every rope stack and 5 Strands as a trade opens. For a partner, `capitol-bot --prefix trade --trade <you> --ask --offer-strands 15` asks you, offers, and accepts once you've offered something. It's account 1 of its prefix, so sign the client in as another (Trade2). With the stack up, `capitol-bot --prefix trade --accounts 2` stocks Trade1 and Trade2 with rope (it lands in the crafting output; the test moves it), then `cargo test -p capitol-client two_clients_trade -- --ignored` runs two sessions through a request, drafts, a reset, the swap and a disconnect. Each run gives Trade1's rope to Trade2, so restock Trade1 (`--accounts 1`) before the next.

**Onboarding (P8.3).** The hints are `ui/hints.rs` and their rules are `capitol_core::onboarding` (`Tour`: which card, what counts as done, `judge` for an old account). Each account's progress is a byte in `save/hints.toml` (gitignored), keyed by server and player id. Delete its line, or the file, to see the hints again. The card keeps clear of the open panels where it can (`hints::place`, #99); check a layout change at 1280×720 with crafting and the inventory both open, the tightest case. The shortcut overlay is `ui/shortcuts.rs`, and its rows are a table there: change it with `config/input.toml`. `?` toggles it (the typed character, in `on_window_event`), and so does F1 (`help`), which `--input-script` can press: `9.0 tap F1`. Esc closes it. To walk a new account through, `capitol-bot --prefix <p> --gather 0` makes one with nothing. The walk step is a `click` on the ground. `POST /world/extract` gathers, and keys do the rest.

**Settings (P8.4)** are `src/settings.rs` (the model and `save/settings.toml`, gitignored) and the panel `ui/settings.rs`, opened by F10 or the header's Settings link, offline too. They apply live: graphics through `Graphics::apply` on `ExtensionGpu`, volumes through `Soundscape::set_volumes`, which sets Flint's buses (music = master × ambience, for the beds; sfx = master) and scales each one-shot by the effects or interface level, and the camera through `cap_setting("camera_sensitivity" | "invert_orbit")` in `camera.rhai`. A new script-facing setting goes in `cap_setting`. The server isn't a setting: it stays in `save/session.toml`. **Captures read your own settings file**, so with shadows off there, a capture has none. Use `--settings-file <path>` for a fixed one (a missing file is the defaults, and nothing is written unless something changes). `--settings-panel` opens the panel. A capture can `click` it; `cargo test -p capitol-client theme` also clicks the switch, the segments and the slider headless.

**Performance (P8.5).** Measure uncapped: `FLINT_VSYNC=0` turns off vsync, and `--exit-after` prints the average ms/frame after the first 2 s. Pair it with `RUST_LOG=warn,capitol=debug` for the draws and the culled count. Run each zoom (`--view street|district|map`) offline, then live with a crowd: `capitol-bot --prefix perfbot --accounts 24 --wander --near <you> --seconds 900`. A crowd that big logs in faster than the server's per-IP auth limit allows (10 a minute, E0.7), so start the backend with `RATE_LIMIT_AUTH_PER_MIN=1000` for it. Other agents' builds on this machine swing the numbers a lot, so check the load first, and A/B by alternating runs rather than comparing against an old figure. To time one script function, wrap it in Rhai's `timestamp()` / `.elapsed` and `log_info` the result. Per-player work in a script should only project and draw. The players' names are `labels.rs` (`cap_name_tags`), for that reason.

**The economy sim (E2.7).** It's `capitol_core::sim`. `sim::plan` is the planner (pure: one step toward a goal, from the catalog and what the bot holds). `sim::Role` and `MIX` are the roles: gatherers of fiber, wood and ore, crafters of planks, ingots and tools, and builders. `sim::report` is the report (pure) and `sim::run` is the swarm. Run it against a backend and database of its own. `create database capitol_sim` in the same container, then start the backend with `DATABASE_URL=…/capitol_sim PORT=3166 SIM_TICK_SCALE=10 RATE_LIMITS=off`. The limits must be off because bots at ten times the pace go over every one. Then `cargo run -p capitol-core --bin capitol-bot -- --server http://127.0.0.1:3166 --sim 20 --hours 2`: two game hours take twelve minutes. The report is printed and written to `renders/sim/sim-<stamp>.md` and `.csv` (gitignored). Its "Why steps failed" table masks ids and numbers, so the same refusal counts once. Drop and recreate the database between runs you want to compare. The accounts (`sim1@bots.capitol.local` and up) keep what they made, their plots and their stations. Since E3.8 two market makers join the swarm (`--makers <n>`, accounts `simmaker1@…` and up), funded by a grant, so the backend also needs `DEV_GRANTS=on`. They quote logs, ore, stone, charcoal, planks, ingots and bricks. A bot sells all of its role's product once it holds 20, and buys what a step would have it gather when gathering it isn't its job. Orders are placed at the Exchange hall (E3.4), so each trade walks back to the spawn, up the avenue to the hall and out again. The report's production table gains Traded, Low, Mean price (D5) and High, and the Strands section shows fees and the makers' Strands at the start and end. `--makers 0` runs the swarm with no market, as in E2.7, where each bot climbs its own chain from empty hands. `/health` carries `sim_tick_scale` when it isn't 1, and the report turns wall time into game hours with it.

## Testing against the server

The local stack is `docker-compose up -d` at the repo root, then `cargo run` from `backend/` (API on port 3000). With it up, `cargo test -p capitol-core -- --ignored` runs the live tests: register, login, the WebSocket handshake and a move. Set `CAPITOL_SERVER` to point them somewhere other than `http://localhost:3000`.

**`capitol-bot`** is a headless player for smoke tests and for company:

```bash
cargo run -p capitol-core --bin capitol-bot                          # gather fiber, craft rope, report
cargo run -p capitol-core --bin capitol-bot -- --accounts 5 --wander --near <your player name>
```

Bots log in as `bot1@bots.capitol.local` and up, registering the first time. `--prefix` picks another set. `--help` lists the rest.

**Market makers (E3.8)**: `capitol-bot --prefix maker --accounts 2 --market fiber,plank,iron_ingot --fund` runs two. Each quotes both sides of each item's book round its last trade, or round D5's value before the first one (`market_maker::SEED_PRICES`), and re-quotes as orders fill. `--spread`, `--depth`, `--size` and `--target` tune it. A maker walks to the Exchange hall first, since orders are placed there (E3.4). `--fund` tops a maker up to 20000 Strands and `--target` units of each item through `POST /player/grant`. The server serves that only with `DEV_GRANTS=on`, which no build turns on by itself. With `--seconds` a maker takes its orders down when it stops. On Ctrl-C they stay up, and the next run picks them up again. A bot resumes wherever it last stood, so use `--near` to bring a fleet to you.

The server allows **one session per account**. A second login kicks the first one, so a two-client test (Flint + React, or two Flint) needs two accounts. Clients on this machine can share the local server. A client on another device can't reach it, because the backend listens on `127.0.0.1` (see "Environment Setup" in the root `CLAUDE.md`).

## The engine subtree

The engine lives at `flint-client/engine/` as a squash subtree of `https://github.com/chrischaps/Flint` (primary branch **`main`**). The remote is named `flint`:

```bash
git remote add flint https://github.com/chrischaps/Flint.git   # once, if missing
```

**Pull engine updates** (from the repo root, with a clean tree):

```bash
git fetch flint
git subtree pull --prefix=flint-client/engine flint main --squash
```

**Don't rebase across a subtree merge.** A rebase flattens the merge and drops the squash parent that the next `subtree pull` needs. If master moves under a branch with a subtree merge on it, merge master in. `scripts/issue.sh land` does this itself (#101).

**Engine changes go upstream.** Any change under `engine/` is a Flint change. It goes to Flint as a PR, never as a Capitol-only patch:

1. Make the change in `flint-client/engine/`. Give it an ADR and a Flint book page (`engine/docs/book/`) if it adds API. Flint's ADRs aren't in the engine tree; they're numbered in `C:\Users\chris\dev\Starchild\docs\adr\`, and plan §4.4 records the next free number. Every hook must be opt-in and general enough for any Flint game.
2. Test crate by crate: `cargo test -p <crate>` from `engine/`. `--workspace` fails on Windows because of `ndk-sys`. Don't `cargo fmt` engine files you didn't change.
3. Push to a feature branch and open a PR against `main`:
   ```bash
   git subtree push --prefix=flint-client/engine flint feature/<name>
   gh pr create --repo chrischaps/Flint --base main --head feature/<name>
   ```
4. **Chris merges Flint PRs.** Never push to Flint `main`. Leave the issue open until the merge. Then `git subtree pull` (above) and check that the subtree matches `flint/main`: `git diff flint/main HEAD:flint-client/engine --stat` should be empty.

The only exception was the throwaway P0.4 spike. Its subtree patches (`SPIKE(P0.4)`) live on branch `spike/p0.4` and never reach master or Flint. Keep it that way: a subtree patch on master would ride along in the next `git subtree push`.

**The P1 hooks are in Flint.** H1 to H5 merged as [Flint PR #41](https://github.com/chrischaps/Flint/pull/41) (Flint `main` 1481637), and the subtree was pulled back. `flint-client/engine` matches `flint/main` with no Capitol-only patches. Any engine change from here on follows the steps above: its own `feature/*` branch and PR.
