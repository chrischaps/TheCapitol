# CLAUDE.md: The Capitol, Flint client

The Capitol's 3D client, built on the Flint engine (Rust/wgpu). It's a window onto the Capitol server: Rust handles the wire and the world, and Rhai scripts handle the feel. The plan is `../the-capitol-flint-client.md`, and the work queue is the GitHub issues labelled `flint-client` (use the `next-issue` skill).

## Layout

```
flint-client/
  Cargo.toml          # its own workspace: members crates/*, excludes engine/
  Cargo.lock          # committed; seeded from engine/Cargo.lock
  .cargo/config.toml  # 8 MB main-thread stack on Windows (copied from the engine)
  engine/             # Flint, git subtree (squash). Don't edit casually; see below.
  crates/
    capitol-core/     # net + state, no engine dependency, fast tests
    capitol-client/   # the game binary (`capitol`)
  scenes/ schemas/ scripts/ fonts/ audio/ models/ fixtures/
  particles/          # *.particles.toml effects, loaded by name (the forge's fire, P6.1)
  assets/icons/       # item icons: <item_type>.svg, fallback.svg; style in its README (P5.2)
  play.bat            # build release and run
  renders/            # screenshots and captures (gitignored)
  target/             # this workspace's build output (gitignored)
```

The root `Cargo.toml` (the backend workspace) has `exclude = ["flint-client"]`. Run cargo from `flint-client/`, not the repo root.

**Engine crates are path dependencies.** They're declared once in `[workspace.dependencies]` in `Cargo.toml` (`flint-player = { path = "engine/crates/flint-player" }`). Member crates use `{ workspace = true }`. The engine's own workspace is excluded rather than nested. Its crates still pick up `version.workspace = true` and similar settings from `engine/Cargo.toml`.

**The wire types come from `../protocol`** (crate `capitol-protocol`, a member of the root workspace). It holds the WebSocket enums, REST DTOs, `/terrain` types and shared rules (ranges, zones, quality grades, the water-crossing test). The backend compiles against the same crate, so use its types rather than redefining shapes here. The client leaves its `backend` feature off. Change the protocol from the repo root, and run `cargo test -p capitol-protocol` there.

**Match the engine's versions.** A third-party crate that crosses the engine boundary (egui, winit, wgpu, rhai, glam) must use the same version as `engine/Cargo.toml`. Otherwise two copies get linked and the types don't line up.

## Build and run

```bash
cd flint-client
cargo build                         # debug, about 45 s from cold
cargo test -p capitol-core          # fast; no engine
play.bat [args]                     # release build, then target\release\capitol.exe [args]
```

From bash, run `play.bat` through PowerShell with an absolute path:
`powershell.exe -NoProfile -Command "cmd /c 'C:\Users\chris\dev\TheCapitol\flint-client\play.bat'"`.

If another build or a running client could lock the exe, use your own `CARGO_TARGET_DIR`.

**Profiling (D5.4).** F2 (or `--stats`) shows the GPU's time per phase beside the draw counts (Flint ADR 0108), and `--exit-after` with `--stats` prints it as `[perf] avg GPU … ms/frame`. For the CPU, `cargo build --release -p capitol-client --features profile` builds the client with Flint's frame profiler (ADR 0109): run [Tracy](https://github.com/wolfpld/tracy/releases)'s viewer beside it to see the frame loop, the renderer and wgpu scope by scope. It listens on loopback only. The game's own panels in F3 come from `PlayerExtension::debug_panels` (ADR 0107). The book's *Profiling* and *Debug Panels* pages have the rest.

**Packaging (P8.7).** `powershell -NoProfile -File package.ps1` builds into `target\package` with a static C runtime (`+crt-static`, so no VC++ redistributable; its `RUSTFLAGS` repeat the 8 MB stack, because they replace `.cargo/config.toml`'s). It stages `dist\TheCapitol\` and zips it as `dist\TheCapitol-<git describe>.zip` (`dist/` is gitignored at the root). The zip holds the exe, the game's data dirs, `engine\schemas` (the only engine files read at run time; the shaders are compiled in), `fixtures\terrain.json`, an `Explore offline.bat` and a player's `README.txt`. **A new data dir the game reads must be added to the script's list.** The game finds its data beside the exe when the working directory lacks the scene (`enter_game_dir` in `main.rs`), so the zip runs from a shortcut or any terminal; paths given on the command line are made absolute first. To check a package, unzip it outside the repo and run it from another folder: offline, then with `--server`, then signed in (a `save\session.toml` with `server`, `email`, `refresh_token` and `token_server` keys skips the form).

**Showcase.** `powershell -NoProfile -File tools\showcase.ps1` writes offline stills of every fixed `--view` and a crane shot (`capitol.mp4`, ffmpeg) into `renders\showcase\`. It runs with `--clean` (offline only: no inscription panel and no free-point mark) and its own settings file (High shadows). The clip is `--camera-path tools\showcase-path.txt` ([#92](https://github.com/chrischaps/TheCapitol/issues/92)): the tower on the wilderness horizon, then round and in over the rings and up to the map. **Teasers.** `powershell -NoProfile -File tools\teaser.ps1 [-Cut ig,yt,tour] [-Scale 0.25]` films the shot library (`tools\shots\shots.psd1`: a camera path, a time of day and sample flags each) and cuts the Instagram reel (1080x1920), the YouTube teaser and the YouTube tour (3840x2160) from `tools\shots\cuts\*.psd1`, which hold each cut's segments, titles, end card and a score of the game's own sounds ([#343](https://github.com/chrischaps/TheCapitol/issues/343)). Shots render once per frame shape into `renders2\shots-*` and are reused until `-Rerender`; `-Scale 0.25` drafts the lot in minutes. A 4K cut is two ffmpeg runs, one version each, because one run with both ran the machine out of memory.

## Terrain, offline mode and captures

`capitol` fetches `/terrain` from the server and caches it in `cache/terrain-<host_port>.json` (gitignored). A cached terrain is drawn at once and revalidated by version: the server answers 304 while it's current. The server is `--server` (or `CAPITOL_SERVER`) for one run, otherwise the one last chosen on the login form, otherwise `http://localhost:3000`.

**Login (P4.1).** Online, the client opens on the login form (`ui/login.rs`), with the camera circling the tower behind it (`camera.rhai`, `cap_at_login`). A stored token goes straight in. The way in is `capitol_core::auth::Auth`, which is pure and unit-tested; `session.rs` owns the `Net`, the store and the poller, and runs it. The server, the last email and the token live in `save/session.toml` (gitignored; never commit it), not in the scripts' `save/persist.toml`. Delete the file, or Sign out (top right), to see the form again. **Players (P4.2)** are `entities.rs`: an avatar entity per `Motion` pose, with fades on join and leave. A citizen (C0.2) carries a pale, steady lantern where a person's amber one gutters, and a lozenge before the name (`labels.rs`, `hud.rhai`). Offline, `--citizen-sample` stands people, citizens and you in a row where the camera looks, half a second in. Frame it with one `--camera-path` key, `0 -56.2 2.1 334.8  -55 1.1 330`. **Speech (Commons S1.2)** hangs over the names in `labels.rs` (`Bubble`, from `PlayerLabel.line`, which the extension fills from the session's `capitol_core::talk::Log`) and is drawn by `hud.rhai`'s `bubble`; `--talk-sample` with `--citizen-sample` has the row talk at 1 s, 3 s and 5 s, a long line among them, so a capture at 6 s shows all three (`--clean` keeps the offline inscription off them). From street zoom, `0 -60.5 10 348  -55 1.1 330` shows the names crowding and the bubbles stacking with captions. `cargo test -p capitol-client labels` checks the wrap, the ellipsis, the slide and lift, the captions and the speakers kept; `cargo test -p capitol-core talk` the log. `--citizen-sample stroll` walks them up and down the way the camera looks instead, as if along a street, for films ([#346](https://github.com/chrischaps/TheCapitol/issues/346)): with `--bazaar-sample street` and `0 -5 2.3 29.75  -16 1.3 29.75` at dusk they pass under the bunting. Their names are `scripts/hud.rhai`, and so is the zone banner (P4.5). The header strip and the reconnecting overlay are `ui/hud.rs`. **Clicks (P4.3)** are `scripts/input.rhai`: a left click on the ground goes through the click priorities (React's order, 1–5 still empty) to `cap_move`. Every walk goes round the water by the walk graph (#267): `terrain.rs` builds `capitol_core::paths::WalkGraph` on a thread of its own, `Session::walk` plans it with `paths::Walk` and sends a `move` a leg, and `cap_route()` gives the scripts the corners still to pass, so the dashes run round them. Until the graph is in, or where there's no way round, the walk is straight, and a canal stops it with `movement_blocked`, which the extension fires at the scripts. `cargo test -p capitol-client a_click_across_the_canal -- --ignored` walks `Walk1` (`capitol-bot --prefix walk --gather 0`) over the outer canal by a bridge. **Resource nodes (P4.4)** are `nodes/` (every kind since E2.5, below) and priority 5 in `input.rhai` (`cap_node_at`, `cap_extract`, the rings and toasts). The click rule, extract or walk then extract, is `capitol_core::harvest`. To extract without clicking, `POST /world/extract` with the account's token while the client is connected. The client sees it like its own. **Input scripts click (H16, Flint ADR 0082):** `3.0 click 640 360` moves the pointer, presses and releases on three frames, `mouse x y [secs]` moves or glides it (a drag, with `down`/`up MouseLeft`), and `MouseRight` etc. work with `down`, `up` and `tap`. Positions are the screenshot's pixels. The pointer goes through egui first, as a real one does, so a click on a panel presses its button and never reaches the world. **Keys reach egui too (H27, Flint ADR 0097):** a held `down ShiftLeft` is on the drags that follow (a shift-drag split), `tap Enter` and `tap Escape` work in a focused field, and `type 200` types into it (click the field first). A key typed into a focused field never reaches the game. Extensions see scripted keys through `PlayerExtension::on_key` (H29, Flint ADR 0103, [#273](https://github.com/chrischaps/TheCapitol/issues/273)), never `on_window_event`, so the game reads its own keys there: `tap Slash` with `down ShiftLeft` held is `?` for the shortcut overlay, and `tap Escape` closes it or stops a placing. Keep the real cursor off the window during a capture. To reach a canal fast, walk there first with `POST /player/move` while the client is connected. To see a crowd, run `capitol-bot --accounts 10 --wander --near <your name>`. A stored token in `save/session.toml` is the easy way to put a capture in the world without typing into the form. Once signed in, the session hears `terrain_updated` (an admin regenerating the world from the React client's F2 tweaker) and rebuilds the world. Only the layers whose inputs changed are rebuilt (`world::Rebuild`). The form can be typed into from `--input-script` since H27: `click` a field, then `type` into it. Before that, P4.1 drove it with keys posted to the client's window by PID (its closing comment on #31). `--offline <file>` builds the world from a `/terrain` JSON with no server at all, so there's no login either: the rig, as before. `fixtures/terrain.json` is a captured one; refresh it with `curl -s -o fixtures/terrain.json http://localhost:3000/terrain`.

Every visual change is checked with a capture, run from `flint-client/`:

```bash
target/release/capitol.exe --offline fixtures/terrain.json --screenshot-at 3 --exit-after 4
```

That writes `renders/capitol.png`. The camera is the rig in `scripts/camera.rhai` (P3.9; since E3.13 its near end stands over your shoulder, rises or pulls in out of the buildings' walls and roofs, which the layers upload as ray targets (`world::mesh::RAY_TARGET`, Flint ADR 0105, #293) and `clear_line` meets through `raycast_meshes`, swings behind you as you walk close in, and eases down to the shoulder in the bazaar; `--view bazaar` puts the free point in the bazaar's lane for that): signed in, it follows your avatar and WASD or the arrows pan from it (P4.2). Offline, WASD moves a free point, the wheel or R/F zoom from 15° over the street to the map, Q/E or a right-drag orbit, H comes home. Keys are in `config/input.toml`. `--view` picks where it starts: `street`, `district` and `map` are rig zooms. `bridge|suburb|urban|capitol|crown|from-urban|from-suburban|from-rural|from-wilderness|range` are fixed shots (bridge stands on a canal quay; suburb is low over curving streets; urban is close over the urban lots; capitol looks up at the tower from beyond the moat; crown is level with its lantern; each from-* puts the tower on the horizon from that zone; from-wilderness stands on a ridge of the north-west massif and looks down over the valleys to it, and range looks east along the ranges from the southern summit, W11). A shot holds until the first camera input, then eases into the rig. The rig takes up what the shot was looking at, zoomed out just enough to keep a raised subject like the crown mid-frame and no wider than `district`, so Q/E orbit round it. **To film a deliberate move,** pass `--camera-path <file>` (offline only). The file has one key a line, `t px py pz tx ty tz`: game seconds, then where the camera stands and what it looks at, in world metres. It plays as a moving shot on a monotone cubic, starting and ending at rest; a repeated key is a hold. It stays at its last key until camera input lets go into the rig. The format is in `camera_path.rs`, and `tools/showcase-path.txt` is an example. For motion from held keys instead, add `--frame-step 0.016666667 --screenshot-every 0.25` with an `--input-script` (`2.0 wheel 3` scrolls three notches in; R/F zoom at a steady rate) for numbered, deterministic frames. `cargo test -p capitol-client camera_rig` checks the rig's geometry: no clipping, the tilt curve, the horizon, the map. `--screenshot <path>` names the file, `--input-script <file>` plays timed keys and the wheel (flint-player's format: `1.0 tap KeyE`, `1.0 wheel -2`), and `--exit-after` prints the average ms/frame and, on a second `[perf]` line, the average draw calls, entity draws, culled draws and triangles. `--stats` opens F2's rendering stats overlay from the first frame, and an input script can tap F2 (or F3/F4) like a real key (H9). The old `RUST_LOG=capitol=debug` stats log is gone: use those instead. Look at the PNG before calling a visual change done. The scene is `scenes/capitol.scene.toml` (dusk: sky, sun, fog and post). The dusk is the evening of the day (`daylight.rs`, P8.6a): online the light follows the server's clock, and offline it's evening unless `--time-of-day <0..1>` says otherwise (0 is midnight, 0.25 dawn, 0.5 noon, 0.8 evening). The `sun` and `fill` lights and the sky are rewritten as the hour moves, so tune the dusk in the scene file and the other hours in `daylight.rs`. Its fog thins as the camera climbs over the land under it (W11) and is gone by 250 m (density zero; fog stays on, and since Flint ADR 0078 it reaches everything drawn, water included, so `far` is just past the 5 km ground skirt), and from 280 m to 600 m the light flattens into the map's palette (`atmosphere.rs`), so a high view shows neither. Far things take a slate-blue haze, the fog's aerial tint (Flint ADR 0101, #233: `fog_tint_*` in the scene for the dusk, `daylight::Palette::aerial` for the other hours), and the valleys a mist at dawn and dusk (W11, `world/mist.rs`), both clearing with the fog. Since #297 the mist is air, not sheets: Flint's ground fog (ADR 0106) on a map whose floor is the ground and whose amount is how thick the mist lies (`world::mist::build`, uploaded with `ExtensionGpu::set_ground_fog` when the land comes in), its density, colour and falloff set by the hour in `atmosphere.rs` (`mist::DENSITY`, `FALLOFF`, `colour`). F3's Fog section tunes it live (Ground density, colour, falloff, steps). To see it from inside, stand in a hollow at dawn: `--camera-path` with one key `0 -46 8 -634  54 6 -634` and `--time-of-day 0.26`.

## The UI theme

All egui panels take their look from `crates/capitol-client/src/ui/theme.rs` (P5.1, plan §4.3). It holds the colour tokens, egui's `Style` and `Visuals`, the fonts, and the parts panels are made of (`panel`, `well`, `tray`, `header`, `pill`, `primary_button`, `accent_button`, `grade_badge`, `quality_badge`, ...). **Panels use no colours or sizes of their own.** If a panel needs one that's missing, add it to `theme.rs`. `theme::install` runs at the top of `CapitolExtension::ui` and sets the style once.

The fonts are in `fonts/`: Source Sans 3 (text) and Cinzel (titles), both OFL, with licences beside them. Flint installs them for the script HUD and egui alike. `fonts.toml` names them `body`, `strong` and `display` (`draw_text_opts(..., #{ font: "display" })`, `FontFamily::Name("strong")`), and its `[egui]` table makes `body` egui's default face (Flint ADR 0081, #72). Don't call `set_fonts` from the game: Flint's next font install would drop it. A font that can't live in `fonts/` goes through `PlayerExtension::fonts`. Tests that draw the theme take their context from `theme::test_context()`, which loads the fonts Flint would.

Review a theme change side by side with the React client, from `flint-client/` (the steps are in the file's header comment too):

```bash
target/release/capitol.exe --offline fixtures/terrain.json --ui-sample --width 1920 --height 1080 --screenshot renders/p5.1-sample-flint.png --screenshot-at 3 --exit-after 4
target/release/capitol.exe --offline fixtures/terrain.json --width 1920 --height 1080 --screenshot renders/p5.1-world.png --screenshot-at 3 --exit-after 4
"/c/Program Files/Google/Chrome/Application/chrome.exe" --headless --allow-file-access-from-files --window-size=1280,720 --force-device-scale-factor=1.5 --screenshot="$(cygpath -w $PWD/renders/p5.1-sample-react.png)" "file:///$(cygpath -m $PWD/tools/theme-sample.html)"
```

`tools/theme-sample.html` is the sample's two panels in the React markup and CSS, with the panel-less world capture as the backdrop.

**Slots (P5.3).** Every container is drawn with `ui::slots::SlotGrid::new(&container).show(ui, &mut icons)`, which returns `Option<Move>`. Send the move with `session.move_item(m)`, and show `session.move_refused(now)` when it's `Some`. Don't draw slots by hand. A drag between any two grids on screen just works (egui DnD payload). **The inventory panel (P5.4)** is `ui/inventory.rs`, bottom right, toggled with `I` (the `inventory` action, so `--input-script` can press it) or the header's Inventory chip. `--containers` shows, bottom left, any container no panel has taken. Today every type has its panel, so it's empty. `--ui-sample`'s grids move, merge and swap locally, so the widget can be tried offline. `cargo test -p capitol-client slots` drives drags headless. With the stack up, `capitol-bot --prefix slots` once, then `cargo test -p capitol-client a_move_reaches -- --ignored`, checks the server round trip. Captures drag with the input script's pointer (`1.0 mouse 950 345`, `1.2 down MouseLeft`, `1.3 mouse 1105 425 0.5`, `2.0 up MouseLeft`), and a hover of half a second shows the tooltip. `--ui-sample` is the offline bench for it.

**Crafting (P5.5).** The panel is `ui/crafting.rs` and its rules are `capitol_core::craft`. `Session::craft(now, recipe_id)` checks and sends; `Session::crafting()` is where the craft stands. The ring and the finish are in `scripts/input.rhai` (`cap_players()`' `craft`, and the `crafting_completed` event). C (the `crafting` action) or the header's Crafting chip toggles the panel, and Enter (`craft`) crafts, so an `--input-script` can craft: `7.0 tap Enter`. With the stack up, `cargo test -p capitol-client rope_then -- --ignored` runs Fill, rope, a blocked kit, a cancel and the kit through `Session`. It gathers its own fiber on `craft1@bots.capitol.local`. To stock any account for a capture, use `capitol-bot --prefix <p> --gather <n>`. Arrange the boxes with input-script drags, or beforehand with `POST /inventory/move` using the token in `save/session.toml`.

**Stations (P6.1)** are `stations.rs` (the models, from the store) and `draw_station_ring` in `input.rhai` (from `cap_stations()`). The reach rule is `capitol_core::station`, the place for P6.2's placement checks too. The forge's fire is `particles/forge.particles.toml`: Flint loads every effect in `particles/` at start, and `stations.rs` names it in a `particle_effect` component. The kiln's smoke is `particles/kiln.particles.toml`. Since E2.6 every catalog station has a model (a new type without one is a plank crate; `every_catalog_station_has_its_own_model_and_unknown_ones_a_crate` fails until it gets one), and fired ones glow brighter at night (`Stations::fires`). To see them all offline, `--station-sample` stands one of each in a row where the camera looks, 0.5 s in. Frame it with a `--camera-path` that holds still past 0.5 s, e.g. one key `0 -46.9 2.3 336.2  -50.4 0.7 330.1` in the rural ring, and add `--time-of-day 0.02` for night. **The station panel (P6.3)** is `ui/station.rs`, bottom right beside the inventory. Where two columns don't fit left of the inventory, it stacks them in one, and it's never taller than the screen under the header strip: the header, the tabs and the footer stay put and the columns scroll (`theme::scrolled`, whose foot fades while there's more below; #235). Offline, `--station-panel-sample craft|automation` opens it on a workbench of yours beside the inventory and crafting panels; check it at `--width 1280 --height 720` (853×480 points at 150%). To capture it scrolled, point at the columns and turn the wheel: `1.0 mouse 689 400`, `1.2 wheel -10`. A scripted wheel goes through egui as a real one does ([#299](https://github.com/chrischaps/TheCapitol/issues/299)), so it scrolls the panel under the pointer and never zooms the camera behind it. Click a station (`input.rhai` priority 3, `cap_station_at`), or press O for the nearest one. Out of reach, you walk to it first (`capitol_core::station::Visit`). Enter crafts at the open station. So an `--input-script` can open one and craft: `3.5 tap KeyO`, then `8.0 tap Enter`. Every station recipe is content (`backend/content/recipes.toml`, D5 since E2.4): the workbench's simplest is `tool_handle` (2 sticks and a rope), and the forge kit takes bricks, stone and rope under a hammer. Its output lands in the player's crafting output slot, not the station's box.

Placing a station needs a kit and an owned plot (P6.2, below), so for a quick test insert rows straight into the local DB beside an account. Give each its `station_inventory` container, or `open_station` answers "Station has no container":

The live station test crafts a tool handle, and fallen branches have no nodes until E2.3 (#162), so give `Stations1` its two sticks the same way:

docker exec capitol-postgres psql -U capitol -d capitol -c "insert into items (id, item_type, quality, quantity, owner_id, container_id, slot_index) select gen_random_uuid(), 'sticks', 50, 2, p.id, c.id, (select coalesce(max(slot_index), -1) + 1 from items where container_id = c.id) from players p join containers c on c.owner_id = p.id and c.container_type = 'player_inventory' where p.name = 'Stations1'"

**Restart the backend afterwards** if you'll craft at them: the tick loads stations only at startup or from `place_station`, and `craft_at_station` checks its own list ('Cannot access station'). Opening one and moving items work without a restart. `capitol-bot --prefix stations --gather 0` makes `Stations1` at the spawn, and its password is `stations-1-capitol-bot`, so `POST /auth/login` with `"refresh": true` gives the `refresh_token` for `save/session.toml` (without it there's no refresh token, and the form shows). Rows inserted this way fire no `station_placed`, so they rise rather than drop. Delete them when you're done, because new players spawn right there. P6.3 tested on its own database instead: `create database capitol_45` in the same container, with `DATABASE_URL` and `PORT` in the worktree's `backend/.env`. That keeps a new migration off the shared DB until it lands; a backend whose folder lacks an applied migration refuses to start. With a workbench and a chest for `Station1`, `cargo test -p capitol-client a_station_opens -- --ignored` runs it all through `Session`: walk and open, Fill, craft a tool handle, the chest in and out, walk away, remove. It removes the chest.

**Tools and wear (E1.7).** A tool's slot shows a wear bar in place of the quantity, and its tooltip the numbers the server uses (`slots::tool_lines`; the catalog reaches the slots through `slots::know_catalog`, once a frame). The craft check counts the tool term: `craft::tool_for` (or `tool_in` from a `GameState`) picks the tool as the server does, and the preview's bar, key, tool line and lifts are `crafting::preview`, shared with the station panel. The station's tool slot is `station::tool_slot`; a drop on it is `install_tool`, and a drag of the installed tool onto any slot becomes `remove_tool` in `Session::move_item`. A broken tool shatters where its slot was last drawn (`slots::shatter`, from `tool_broke`). Offline, `--ui-sample` shows sickles at three wear levels, breaks one at 6 s (`--frame-step 0.016666667 --screenshot-every 0.05` to film it), and its preview is the real one; hover a sickle with `1.5 mouse 1667 861` at 1920×1080 for its tooltip. Since E2.4 the anvil's four heads and the four station kits take a hammer, so a tool term shows live at an anvil, or at a workbench on `craft_kiln`.

**Automation (E4.4).** The rules are `capitol_core::automation` (`Status`, `Work`, `pause_words`, the form's `Draft`); `Session::start_automation` and `stop_automation` send them, and `automation_refused` is the server's no. The tab is `ui/automation.rs`, in the station panel for the station's owner. In the world, `stations.rs` lights each station by its work (`work_light`, over the hour's `fire_light`, through `material.emissive_scale`): the fires and the lanterns on the workbench, sawbench, anvil and crate. Each craft blows a puff (`particles/craft_sparks`, `craft_wisp`) from an entity of its own, and an ember floats over your own paused ones (`draw_station_ember` in `input.rhai`, from `StationMark.paused`). Pauses are `automation_note` toasts, live or replayed on login. **The wilds' water (W10)** is `world/wild_water.rs`: three Flint water bodies (`wild_rivers`, `wild_streams`, `wild_lakes`, ADR 0094), built on the land's worker thread and uploaded with it (`Sampled::water`). To look: `0 -371.9 33.9 -438.5  -449.8 3.9 -463.0` follows a river off the rim to its pond, `0 547.8 36.1 -174.9  641.0 6.1 -79.8` looks down a valley it crosses a ridge by, and `0 -200 260 -700  -440 4 -470` takes in the rim from the air. `cargo test -p capitol-client edge_water` checks every course runs on, falls, keeps to its bed and its valley, bends no tighter than its width allows, and leaves the land inside the edge the server's.

The shortcut overlay is `ui/shortcuts.rs`, and its rows are a table there: change it with `config/input.toml`. `?` toggles it (the typed character, in `on_window_event`), and so does F1 (`help`), which `--input-script` can press: `9.0 tap F1`. Esc closes it. To walk a new account through, `capitol-bot --prefix <p> --gather 0` makes one with nothing.

**Settings (P8.4)** are `src/settings.rs` (the model and `save/settings.toml`, gitignored) and the panel `ui/settings.rs`, opened by F10 or the header's Settings link, offline too. They apply live: graphics through `Graphics::apply` on `ExtensionGpu`, volumes through `Soundscape::set_volumes`, which sets Flint's buses (music = master × ambience, for the beds; sfx = master) and scales each one-shot by the effects or interface level, and the camera through `cap_setting("camera_sensitivity" | "invert_orbit")` in `camera.rhai`. **Controls** (T1.1) are the `[controls]` table: `mode` (`click`, point and walk, the default, or `direct`, over the shoulder), `look_sensitivity` and `invert_look_y`, read through `cap_setting("control_mode" | "look_sensitivity" | "invert_look_y")`. F8 (the `control_mode` action, so an input script can press it) swaps the mode live, stops any walk and toasts the new mode, and `camera.rhai` drops its pan on the way back to Click. `--controls click|direct` wins over the file, and offline runs and captures (`--exit-after`, `--input-script`) are Click unless it says otherwise, so a capture never takes your saved mode. A pinned mode lives for the run alone: F8 and the panel change it, and the file keeps yours. Until T1.3 (#321) Direct is only a name: clicks still walk. A new script-facing setting goes in `cap_setting`. The server isn't a setting: it stays in `save/session.toml`. **Captures read your own settings file**, so with shadows off there, a capture has none. Use `--settings-file <path>` for a fixed one (a missing file is the defaults, and nothing is written unless something changes). `--settings-panel` opens the panel. A capture can `click` it; `cargo test -p capitol-client theme` also clicks the switch, the segments and the slider headless.

**Performance (P8.5).** Measure uncapped: `FLINT_VSYNC=0` turns off vsync, and `--exit-after` prints the average ms/frame after the first 2 s. Pair it with `RUST_LOG=warn,capitol=debug` for the draws and the culled count. Run each zoom (`--view street|district|map`) offline, then live with a crowd: `capitol-bot --prefix perfbot --accounts 24 --wander --near <you> --seconds 900`. A crowd that big logs in faster than the server's per-IP auth limit allows (10 a minute, E0.7). A debug backend lets loopback sign in 1000 times a minute (#239), so that's enough on this machine; against a release backend or from another machine, start it with `RATE_LIMIT_AUTH_PER_MIN=1000`. Other agents' builds on this machine swing the numbers a lot, so check the load first, and A/B by alternating runs rather than comparing against an old figure. To time one script function, wrap it in Rhai's `timestamp()` / `.elapsed` and `log_info` the result. Per-player work in a script should only project and draw. The players' names are `labels.rs` (`cap_name_tags`), for that reason.

**The dev overlay (D5.2)** is `ui/dev_overlay.rs`: F7 (the `dev_overlay` action) opens it anywhere, offline and at login too. It shows the frame times (`pre_update`'s dt, the last 240), the net and the prediction (`Session::net_stats`, D5.1), the engine's entities and the store's counts, and your interest cell (`rules::interest_cell`, the server's). An input script presses it with `1.0 tap F7`. `--dev-sample` opens it offline on sample net and world numbers, for the online layout: check it at 1280×720 (853×480 points at 150%). `cargo test -p capitol-client dev_overlay` checks the sentences, the frames' percentiles and the cell. F2 to F4 are the engine's overlays, and F8 is the control mode's (#319). **For an admin (D5.3)** the card grows a third column, the server: the tick from the newest of the Observatory's samples, the last annotations (a watch firing in red), and the tunables off their defaults, read-only. `capitol_core::admin::Watch` polls them while the card is open, only when `auth_ok` said `is_admin`. `--dev-sample` shows that column too. **F6** (`debug_layer`, admins only) steps through the world layers drawn by `scripts/debug.rhai` from `cap_debug()` (`debug_layers.rs`): interest cells, nodes on their ground, the walk graph, and the walkers (`/admin/walkers`, polled once a second), then all of them, then off. To see them, make an account an admin (`update accounts set is_admin = true where email = …`), sign in, and run `capitol-bot --accounts 6 --wander --radius 150` beside it for walkers. An input script presses `tap F6`. The town's own server takes them once it runs a build that has them.

**The economy sim (E2.7).** It's `capitol_core::sim`. `sim::plan` is the planner (pure: one step toward a goal, from the catalog and what the bot holds). `sim::Role` and `MIX` are the roles: gatherers of fiber, wood and ore, crafters of planks, ingots and tools, and builders. `sim::report` is the report (pure) and `sim::run` is the swarm. Run it against a backend and database of its own. `create database capitol_sim` in the same container, then start the backend with `DATABASE_URL=…/capitol_sim PORT=3166 SIM_TICK_SCALE=10 RATE_LIMITS=off`. The limits must be off because bots at ten times the pace go over every one. Then `cargo run -p capitol-core --bin capitol-bot -- --server http://127.0.0.1:3166 --sim 20 --hours 2`: two game hours take twelve minutes. The report is printed and written to `renders/sim/sim-<stamp>.md` and `.csv` (gitignored). Its "Why steps failed" table masks ids and numbers, so the same refusal counts once. Drop and recreate the database between runs you want to compare. The accounts (`sim1@bots.capitol.local` and up) keep what they made, their plots and their stations. Since E3.8 two market makers join the swarm (`--makers <n>`, accounts `simmaker1@…` and up), funded by a grant, so the backend also needs `DEV_GRANTS=on`. They quote logs, ore, stone, charcoal, planks, ingots and bricks. A bot sells all of its role's product once it holds 20, and buys what a step would have it gather when gathering it isn't its job. Orders are placed at the Exchange hall (E3.4), so each trade walks back to the spawn, up the avenue to the hall and out again. The report's production table gains Traded, Low, Mean price (D5) and High, and the Strands section shows fees and the makers' Strands at the start and end. `--makers 0` runs the swarm with no market, as in E2.7, where each bot climbs its own chain from empty hands. `/health` carries `sim_tick_scale` when it isn't 1, and the report turns wall time into game hours with it.

**Citizens (C1.1).** `capitol-town` (`capitol_core::citizen::town`) keeps a roster of citizens living in the world, each playing a sim role on its own thread until Ctrl-C. Mint them first, with an admin account (`update accounts set is_admin = true where email = …`): `CAPITOL_ADMIN_EMAIL=… CAPITOL_ADMIN_PASSWORD=… cargo run -p capitol-core --bin capitol-town -- mint --count 20` appends each to `town.toml` with its key (git-ignored; `town.example.toml` is the shape). Then `cargo run -p capitol-core --bin capitol-town` runs them, printing a health line a citizen every minute and writing it to `town.status`, which `capitol-town status` prints. Citizens get no grants (D2), so they need no `DEV_GRANTS`, and they keep the server's own pace and limits. A citizen rides out a backend restart; one that can't sign in starts again after a backoff, and one whose key is refused retires. To play among citizens without doing all that by hand, `scripts/town.sh up` (#337, at the repo root) runs a town: a backend on a database and port of its own (`capitol_town`, 3300), its admin and a roster in `town/`, and the citizens; `play.bat --server http://127.0.0.1:3300` plays in it.

## Testing against the server

The local stack is `docker-compose up -d` at the repo root, then `cargo run` from `backend/` (API on port 3000). With it up, `cargo test -p capitol-core -- --ignored` runs the live tests: register, login, the WebSocket handshake and a move. Set `CAPITOL_SERVER` to point them somewhere other than `http://localhost:3000`.

**`capitol-bot`** is a headless player for smoke tests and for company:

```bash
cargo run -p capitol-core --bin capitol-bot                          # gather fiber, craft rope, report
cargo run -p capitol-core --bin capitol-bot -- --accounts 5 --wander --near <your player name>
```

Bots log in as `bot1@bots.capitol.local` and up, registering the first time. `--prefix` picks another set. `--help` lists the rest.

**Market makers (E3.8)**: `capitol-bot --prefix maker --accounts 2 --market fiber,plank,iron_ingot --fund` runs two. Each quotes both sides of each item's book round its last trade, or round its target price before the first one (D5's value, `target_price` in `backend/content/items.toml`, on the catalog since D2.3), and re-quotes as orders fill. `--spread`, `--depth`, `--size` and `--target` tune it. A maker walks to the Exchange hall first, since orders are placed there (E3.4). `--fund` tops a maker up to 20000 Strands and `--target` units of each item through `POST /player/grant`. The server serves that only with `DEV_GRANTS=on`, which no build turns on by itself. With `--seconds` a maker takes its orders down when it stops. On Ctrl-C they stay up, and the next run picks them up again. A bot resumes wherever it last stood, so use `--near` to bring a fleet to you.

An account can be signed in on **several clients at once** (E0.8), but **only one plays the avatar**: the newest. The others show a "Playing on another device" banner with Play here, and can still use the market and automation. So two clients on one account test presence, and a two-player test needs two accounts. Clients on this machine can share the local server. A client on another device can't reach it, because the backend listens on `127.0.0.1` (see "Environment Setup" in the root `CLAUDE.md`).

## The engine subtree

The engine lives at `flint-client/engine/` as a squash subtree of `https://github.com/chrischaps/Flint` (primary branch **`main`**). The remote is named `flint`:

```bash
git remote add flint https://github.com/chrischaps/Flint.git   # once, if missing
```

**Pull engine updates** (from the repo root, with a clean tree):

```bash
git fetch flint
git subtree pull --prefix=flint-client/engine flint main --squash
```

**Don't rebase across a subtree merge.** A rebase flattens the merge and drops the squash parent that the next `subtree pull` needs. If master moves under a branch with a subtree merge on it, merge master in. `scripts/issue.sh land` does this itself (#101).

**Engine changes go upstream.** Any change under `engine/` is a Flint change. It goes to Flint as a PR, never as a Capitol-only patch:

1. Make the change in `flint-client/engine/`. Give it an ADR and a Flint book page (`engine/docs/book/`) if it adds API. Flint's ADRs aren't in the engine tree; they're numbered in `C:\Users\chris\dev\Starchild\docs\adr\`, and plan §4.4 records the next free number. Every hook must be opt-in and general enough for any Flint game.
2. Test crate by crate: `cargo test -p <crate>` from `engine/`. `--workspace` fails on Windows because of `ndk-sys`. Don't `cargo fmt` engine files you didn't change.
3. Push to a feature branch and open a PR against `main`:
   ```bash
   git subtree push --prefix=flint-client/engine flint feature/<name>
   gh pr create --repo chrischaps/Flint --base main --head feature/<name>
   ```
4. **Chris merges Flint PRs.** Never push to Flint `main`. Leave the issue open until the merge. Then `git subtree pull` (above) and check that the subtree matches `flint/main`: `git diff flint/main HEAD:flint-client/engine --stat` should be empty.

The only exception was the throwaway P0.4 spike. Its subtree patches (`SPIKE(P0.4)`) live on branch `spike/p0.4` and never reach master or Flint. Keep it that way: a subtree patch on master would ride along in the next `git subtree push`.

**The P1 hooks are in Flint.** H1 to H5 merged as [Flint PR #41](https://github.com/chrischaps/Flint/pull/41) (Flint `main` 1481637), and the subtree was pulled back. `flint-client/engine` matches `flint/main` with no Capitol-only patches. Any engine change from here on follows the steps above: its own `feature/*` branch and PR.
